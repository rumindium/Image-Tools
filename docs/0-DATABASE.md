# 0 — Database

> Four tables, no pixels, no filenames. The database exists to count, to expire, and to explain a failure.
> Last updated: 16 November 2026

---

## 1. What is stored, and what deliberately is not

| Table | Rows are about | Retention |
|---|---|---|
| `jobs` | a server-lane job: tool, status, sizes, timings | 30 days |
| `usage_daily` | counters per session per UTC day | 90 days |
| `model_manifest` | the models a deployment may load | permanent (versioned) |
| `presets_version` | which preset catalog version is live | permanent |

Not stored, anywhere: image bytes, thumbnails, filenames, EXIF, GPS, palettes, data URIs, base64 strings, the
user's IP (only a truncated hash for abuse counters), or a history of which tools a person used. `GET /jobs` shows
this session's jobs because they are *live* (TTL 15 min), and after 30 days the row is a count.

This is not minimalism for its own sake. It is what makes "we cannot leak what we never stored" true, and it is
what makes an eventual accounts feature a `user_id` column rather than a data-migration project.

## 2. Schema

```sql
-- 0001_init.sql
CREATE TABLE jobs (
  id                uuid PRIMARY KEY,                    -- UUIDv7, generated by the API
  session_hash      bytea NOT NULL,                      -- sha256(session id), 32 bytes
  tool_id           text NOT NULL,
  status            text NOT NULL CHECK (status IN
                      ('QUEUED','PROCESSING','COMPLETED','FAILED','CANCELLED','EXPIRED')),
  queue             text NOT NULL CHECK (queue IN ('img-ai','img-heavy')),
  input_file_id     uuid NOT NULL,
  input_bytes       bigint NOT NULL,
  input_pixels      bigint NOT NULL,
  output_bytes      bigint,
  artifacts         jsonb NOT NULL DEFAULT '[]'::jsonb,  -- [{index,name,bytes,format,width,height,hasAlpha}]
  options           jsonb NOT NULL,                      -- the validated options, no user data
  consent_version   text,
  consented_at      timestamptz,
  warnings          text[] NOT NULL DEFAULT '{}',
  error_code        text,
  error_message     text,                                -- already user-safe, scrubbed
  metrics           jsonb NOT NULL DEFAULT '{}'::jsonb,
  idempotency_key   text,
  created_at        timestamptz NOT NULL DEFAULT now(),
  started_at        timestamptz,
  completed_at      timestamptz,
  expires_at        timestamptz
);

CREATE INDEX jobs_session_created_idx ON jobs (session_hash, created_at DESC);
CREATE INDEX jobs_status_expires_idx   ON jobs (status, expires_at) WHERE expires_at IS NOT NULL;
CREATE INDEX jobs_idem_idx             ON jobs (session_hash, idempotency_key)
  WHERE idempotency_key IS NOT NULL;
CREATE INDEX jobs_created_brin         ON jobs USING brin (created_at);   -- for the 30-day purge
```

```sql
CREATE TABLE usage_daily (
  session_hash  bytea NOT NULL,
  day           date  NOT NULL,                          -- UTC
  jobs_created  int   NOT NULL DEFAULT 0,
  jobs_failed   int   NOT NULL DEFAULT 0,
  bytes_in      bigint NOT NULL DEFAULT 0,
  bytes_out     bigint NOT NULL DEFAULT 0,
  inference_ms  bigint NOT NULL DEFAULT 0,
  PRIMARY KEY (session_hash, day)
);
```

```sql
CREATE TABLE model_manifest (
  id             text NOT NULL,
  version        text NOT NULL,
  spdx           text NOT NULL,
  commercial_use text NOT NULL CHECK (commercial_use IN ('true','false','unknown')),
  sha256         char(64) NOT NULL,
  bytes          bigint NOT NULL,
  input_w        int NOT NULL,
  input_h        int NOT NULL,
  dtype          text NOT NULL,
  runtime        text[] NOT NULL,
  upstream       text NOT NULL,
  active         boolean NOT NULL DEFAULT true,
  PRIMARY KEY (id, version)
);

CREATE TABLE presets_version (
  version     text PRIMARY KEY,
  published_at timestamptz NOT NULL DEFAULT now(),
  payload_sha256 char(64) NOT NULL
);
```

### 2.1 Three column choices worth defending

| Column | Choice | Why |
|---|---|---|
| `session_hash` | `sha256(id)` not the id | the DB is one more place a session token could leak; a hash still groups rows without being replayable |
| `artifacts` | `jsonb` array | 1–20 outputs per job with per-artifact dimensions; a child table would be a join for a list that is always read whole |
| `options` | `jsonb`, validated before insert | reproduces "what was asked" for a support question, and contains no filename or pixel |
| `error_message` | text, scrubbed at write | the API's log has the stack; the row has the sentence the user saw |

`expires_at` is nullable on purpose: a `QUEUED` row has no expiry until it completes, because the clock starts
when the user can download, not when they uploaded.

## 3. Transactions that must be atomic

### 3.1 Quota reservation + job insert

```ts
await db.transaction(async (tx) => {
  const day = utcDay();
  const row = await tx.execute(sql`
    INSERT INTO usage_daily (session_hash, day, jobs_created, bytes_in, bytes_out)
    VALUES (${hash}, ${day}, 1, ${bytesIn}, 0)
    ON CONFLICT (session_hash, day) DO UPDATE
      SET jobs_created = usage_daily.jobs_created + 1,
          bytes_in     = usage_daily.bytes_in + ${bytesIn}
      WHERE usage_daily.jobs_created < ${quota.jobs}
        AND usage_daily.bytes_in    < ${quota.bytes}
    RETURNING jobs_created
  `);
  if (row.length === 0) throw new QuotaExceeded();
  await tx.insert(jobs).values({ ...job });
});
```

A read-then-write in two statements lets two concurrent submissions both see `199` and both proceed. The
conditional `ON CONFLICT … WHERE` makes the check part of the increment, so the quota is a fact rather than a
guess. `jobs_failed` is incremented in a separate transaction on failure, and a **refund** (decrement
`jobs_created`) happens only when the job failed before a worker claimed it — a job that failed in inference
consumed real compute and is counted.

### 3.2 Status transitions

```sql
UPDATE jobs SET status = 'PROCESSING', started_at = now()
WHERE id = $1 AND status = 'QUEUED'
RETURNING id;                       -- empty result = someone else claimed it / it was cancelled
```

Every transition is guarded by the expected previous state. That single line is what makes "a cancelled job cannot
be resurrected by a late worker" true in lane B, mirroring the `jobId` identity check in lane A.

## 4. Queries the product actually runs

| Use | Query | Notes |
|---|---|---|
| create job | §3.1 | one transaction |
| claim job | §3.2 | worker |
| progress | Redis pub/sub, **not** the DB | a 100-message progress stream must not write rows |
| poll job | `SELECT … WHERE id = $1 AND session_hash = $2` | indexed by PK, ownership in the same predicate |
| list jobs | `WHERE session_hash = $1 ORDER BY created_at DESC LIMIT 20` + keyset cursor | index `jobs_session_created_idx` |
| download | `WHERE id = $1 AND session_hash = $2 AND status = 'COMPLETED'` | one row, then the filesystem |
| quota read | `SELECT … FROM usage_daily WHERE session_hash = $1 AND day = $2` | |
| TTL sweep | `WHERE status IN (...) AND expires_at < now()` | partial index `jobs_status_expires_idx` |
| purge | `DELETE FROM jobs WHERE created_at < now() - interval '30 days'` in batches of 5 000 | BRIN keeps it cheap |

Progress in Redis rather than Postgres is a deliberate split: the stream is ephemeral by nature, the buffer is
32 events, and writing it to a table would cost 100× the rows for a value that is meaningful for seconds.

## 5. Migrations

- `drizzle-kit generate` produces SQL; the SQL is reviewed and committed (`apps/api/src/infra/db/migrations/`).
- `db:migrate` runs at deploy start, before the API binds a port, and is idempotent.
- A migration that drops a column ships in two releases: stop writing, then drop. Nothing in this schema is
  expensive to keep for one release.
- `jobs.options` is the one untyped payload; a migration that changes its shape must state how old rows are read
  (today: they are read as-is, because `options` is only displayed, never re-executed).

## 6. Retention jobs

| Job | Cadence | Action |
|---|---|---|
| sweep files | 60 s | see [0-FILE-STORAGE](0-FILE-STORAGE.md) §5 |
| expire rows | 60 s (same sweep) | `jobs.status = 'EXPIRED'` after the directory is gone |
| purge jobs | daily 03:00 UTC | delete rows older than 30 days, batches of 5 000, `VACUUM (ANALYZE)` after |
| purge usage | daily | delete `usage_daily` older than 90 days |
| idempotency keys | Redis TTL 10 min | nothing in the DB to clean |

The 30-day purge is the only place a `jobs` row disappears, and by then the artifacts have been gone for 29 days
and 45 minutes. The row's value at that point is aggregate (`usage_daily` already has the counters), so deleting it
costs nothing analytically.

## 7. Capacity, briefly

| Row | Bytes (approx) | 1 000 jobs/day × 30 days |
|---|---|---|
| `jobs` | ~1.2 KB (jsonb artifacts + options) | ~36 MB |
| `usage_daily` | ~80 B per session-day | negligible |
| indexes | ~0.4 KB per job | ~12 MB |

The database will not be the bottleneck at any plausible scale; the AI worker will be. That is the useful thing to
know, and it is why there is no partitioning, no read replica, and no caching layer here.

---

## 8. Why there is no `users` table

The spec requires no account. A `users` table with one anonymous row per session would add a join and a second
identity to keep consistent, and would buy nothing: the session hash already groups everything the product needs
to group. If accounts arrive:

```sql
ALTER TABLE jobs        ADD COLUMN user_id uuid REFERENCES users(id);
ALTER TABLE usage_daily ADD COLUMN user_id uuid REFERENCES users(id);
```

and the anonymous path keeps working through `session_hash`, which is the tenant-first idea applied in the
opposite direction: identity is optional, and the data model does not assume it.
